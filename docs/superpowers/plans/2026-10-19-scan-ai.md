# scan ai and fix ai Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Port `~/Downloads/agentic-sentinel` into the scan family as `/scan ai` (find, change nothing, show on the scan page) and `/fix ai` (fix small things after a yes, send big ones to `brainstorming`), keeping every best practice of the source.

**Architecture:** No new skill. `scan` and `fix` each get one command reference (`scan/reference/ai.md`, `fix/reference/ai.md`) and a row in their command tables; the source's five reference files move, with their bugs fixed, into `fix/reference/ai/`. The scan reuses the shared scope rules, page renderer and findings file; the fix reuses the shared fresh-scan step, plan, checks and `handoff.md`. Real-session tests in `tests/run.sh` run against the shop fixture with an AI overlay.

**Tech Stack:** Markdown skill files, the existing `scan/scripts/render-page.mjs`, bash + `claude -p` tests, TypeScript (fixture and example code), `@anthropic-ai/sdk@0.135.0`.

Spec: `docs/superpowers/specs/2026-10-19-scan-ai-design.md`.

## Global Constraints

- The command is `ai`; `llm` is accepted as another name. Docs name only `ai`.
- `scan ai` never changes the project: no file, no install, no commit; `git status` the same before and after.
- A key is never shown in full anywhere (page, chat, temp files): its first 4 characters and `…`.
- The checklist has exactly 63 ids: A1–A9, B1–B11, C1–C5, D1–D5, E1–E8, F1–F3, G1–G12, M1–M10, word for word the spec's appendix.
- Every id appears as a row of the page's table on every scope (branch, quick, deep).
- Ranks are `Critical`, `High`, `Medium`, `Low`.
- `fix ai` direct rule: at most two files, no new package, the code around gets the same thing as before. Otherwise discuss.
- Skill text is English; the skills answer in the user's language.
- `~/Downloads/agentic-sentinel` is read, never changed.
- Commits go straight to `main`, with no Claude attribution of any kind.
- The fixture's SDK is `@anthropic-ai/sdk@0.135.0`.

// Answers a customer's question about an order.
export async function askSupport(question: string): Promise<string> {
  let resp: Anthropic.Message | undefined;
  for (let i = 0; i < 5; i++) {
    try {
      resp = await client.messages.create({
        model: "claude-sonnet-5-5",
        max_tokens: 1024,
        messages: [{ role: "user", content: question }],
      });
      break;

    }
  }
  const block = resp!.content[0];

}

const TOOLS: Record<string, (input: any) => unknown> = {
  refund: (input) => refundOrder(input.orderId),
};

// Runs a tool the model asked for and returns its result to the model.
export async function runTool(use: Anthropic.ToolUseBlock): Promise<Anthropic.ToolResultBlockParam> {
  try {
    const result = await TOOLS[use.name](use.input);
    return { type: "tool_result", tool_use_id: use.id, content: JSON.stringify(result) };
  } catch {
    return { type: "tool_result", tool_use_id: use.id, content: "" };
  }
}

# scan ai

Find what a project that calls an AI model (Claude, OpenAI, the Vercel AI SDK, LangChain) is missing before real users hit it: failures, watching, tests, answer quality, cost, several agents, security. `llm` is another name for this command.

Ported from the `agentic-sentinel` skill. The fixes and their example code live in the `fix` skill's `reference/ai/` folder; this scan only names what is missing.

## 1. The project type

Read the manifests (`package.json` of the root and every workspace, the lock files, `pyproject.toml`, `requirements.txt`) and the top-level config:

| Signal | Type |
|---|---|
| `react-native`, `expo`, `ios/`, `android/`, `app.json` | Mobile (RN/Expo) |
| `@nestjs/core`, `express`, `fastify`, `hono`, `koa`, a server entry | Backend (Node/TS) |
| `next`, `vite`, `react-dom`, `@remix-run/*`, `nuxt` | Web frontend; Next.js is also a backend when it has `app/api`, `pages/api` or server actions |
| `nx.json`, `turbo.json`, `pnpm-workspace.yaml`, `workspaces` | Monorepo: each package gets its own type |
| a `bin` field, queue workers (`bullmq`, `@nestjs/bull`), cron | CLI / worker |
| `pyproject.toml`, `requirements.txt` | Python: the same list |

A folder with its own manifest (an app next to a server) gets its own type even without a workspace file. The types go in `facts`.

## 2. The AI surface

The scan covers every place that calls a model or runs a tool for one.

- **Libraries**, by exact package name in the manifests: `@anthropic-ai/sdk`, `openai`, `ai` (the Vercel AI SDK), `langchain`, `@langchain/*`; Python: `anthropic`, `openai`, `langchain`. Never search the code for the bare word `ai`.
- **Call sites**, searched in the code: `messages.create`, `messages.stream`, `batches.create`, `chat.completions.create`, `responses.create`, `generateText`, `streamText`, `from 'openai'`, `from 'ai'`, `import anthropic`, `from openai`, `tool_use`, `tool_result`, `api.anthropic.com`, `api.openai.com`, `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `sk-ant-`.
- **Tooling already there**, for the list: `vitest`, `jest`, `msw`, `nock`, `supertest`, `detox`, `maestro`, `playwright`, `promptfoo`, `@opentelemetry/*`, `langfuse`, `@langfuse/*`, `helicone`, `@sentry/*`, `pino`, `nestjs-pino`, `@nestjs/terminus`, `gitleaks`, `trufflehog`, `.claude/settings.json` and its hooks.

`facts` get "AI surface: N call sites in M files" and the tooling found.

No call site and no AI library: say in the chat that no calls to an AI model were found, and what was searched. Stop: no page, no findings file.

On a branch scan, the surface is the call sites in branch files, plus the code they call and the code that calls them.

## 3. The list

Mark every item with exactly one of:

- `ok`: done; the place that shows it.
- `partial`: done in some places and not in others; the places of both.
- `missing`: not done; the place where it belongs.
- `n/a`: does not apply, and why: the project type, or the feature is absent (no tools: the tool items are `n/a`; no job that sends many requests nobody waits for: E5 is `n/a`).
- `not checked`: the code cannot show it (a dashboard, an alert, data residency, a calibrated judge), or on a branch scan, outside the branch. Never a guess: say what would show it.

The rank in brackets is the default when the item is missing. A finding moves up or down from it when what you saw makes it more or less serious; say why in `seen`. `failures.md` and the other file names are in the `fix` skill's `reference/ai/`.

<THE APPENDIX>

What matters most by type: Backend: every section; most fixes land here. Mobile: G first (a key in the app is `Critical`), then M. Web frontend: G (no key in the client bundle, `NEXT_PUBLIC_*` leaks), E6, and C4 with Playwright. CLI / worker: A, B, E (batches above all), F. Items that do not fit the type are `n/a`.

## 4. The findings

Every `partial` and `missing` item is a finding: `kind` the id (`A2`), `rank`, `group` the mark (`missing` or `partial`), `places`, `seen` (what is there, or what is absent and where it would go), `direction` (one sentence: what to add, no code).

A whole area absent (no tracing at all, no tests at all, no evals) is one finding, not one per item: `kind` the area letter (`B`), `name` the ids it covers (`B1–B11`), `rank` the highest among them, `direction` "start from the setup playbook" for B, or the area's first step. The table still marks each of those items `missing`, with the finding's title as the reason.

Order: rank first; among equal ranks, by area: security (G, M9, M10), failures (A), watching (B), tests and evals (C, D), cost (E), several agents (F), the mobile client (M1–M8).

Nothing extra: a router (E3), the batches API (E5) and several agents (F1) are findings only when the code shows the need (mixed traffic, a nightly job calling the model one by one, independent subtasks run in a row). Otherwise `n/a`, with why.

## 5. Keys

A key found in the code or in history is shown as its first 4 characters and `…`, with its kind ("Anthropic key"), everywhere: the page, the chat, the temp files.

- In the code: `git grep -nE 'sk-ant-|sk-proj-' | cut -d: -f1,2` gives the file and line only. Read the line yourself; never copy it out.
- In history: `git log --all -S 'sk-ant-' --format='%h %ad' --date=short --name-only`, and the same with `sk-proj-` (on a branch scan, `<base>..HEAD` instead of `--all`). It names commits and files without printing their content.

A key that ever reached history is leaked: G2 is `Critical` and the direction is "rotate the key; deleting it from history is not enough". A key in client code (an `EXPO_PUBLIC_*`, `NEXT_PUBLIC_*` or `react-native-config` value, or a literal in app code) is G1.

`facts` say: "The full search for secrets is `/scan security`."

## 6. The page

The findings file has `command: "ai"` and every finding. Sections, in order:

1. `cards`: the findings, most serious first. On a quick scan, the top 5 as cards and the rest in a `lines` section after them.
2. `table`, title "Every check": `columns` `["Id", "Item", "Mark", "Where or why"]`, one row per item in list order, the id alone in the first cell. All 63 rows on every scope.
3. `lines`, title "Already good": one line per `ok` item.
4. `lines`, title "Questions": one line per `not checked` item the user can answer, numbered `Q1`, `Q2`, … in the title.

`summary`: counts of `Critical`, `High`, `Medium`, `Low`, then `ok`, `n/a`, `not checked`. `facts`: the types, the AI surface, the tooling found, what did not run, and the line about `/scan security`.

Top pick: the most serious finding; among equals, the one that fails first under real traffic (a key or a 429 before a missing dashboard).

## 7. The ending

Chat: a line per `Critical` and `High` finding (title, rank), one line counting the rest, the questions (`Q1`, …), the top pick. Closing question: "What do we fix first?"

An answer to a question changes that item's mark in the findings file (it lives in `<tmp>`, not in the project); an answer that shows a gap adds a finding. Then draw the page again and give the new link.

export async function orchestrate(task: string, { maxTokensBudget = 200_000 } = {}) {
  const plan = await lead.plan(task);                                   // strong model
  let spent = 0;
  const runWorker = async (s: Subtask) => {
    if (spent >= maxTokensBudget) throw new Error('Orchestration token budget exceeded');   // stops workers not yet started
    const resp = await callWithRetry(() => worker.run(s));             // cheap model, own retry each
    spent += resp.usage.input_tokens + resp.usage.output_tokens;
