# workflow

How the agent responds and recovers: output styles, response shape, and stepping back when stuck.

## User-invoked

- **[explore](./explore/SKILL.md)** — `/explore [topic]` turns the agent into a thinking partner: it reads the code, runs only what looks, draws plain-character diagrams and weighs options, but writes no code and no file (a file only on a separate yes for that one file). It stays on until you say "хватит" / "stop", then gives a three-to-five-line summary — decided, open, next step — and asks before starting that step. Borrowed from OpenSpec's explore, without the `openspec` CLI.
- **[scan](./scan/SKILL.md)** — `/scan <command> [folder] [deep]` reviews what the current branch changed against the default branch (commits and uncommitted changes, every finding that belongs to them, history only from the branch); with no branch changes it looks at the project quickly (top 5), and `deep` looks at the whole project in full. It changes nothing, and shows what it found on one HTML page in the OS temp directory: paths as tiles that open in Cursor, code coloured by kind, proof for every finding. `architecture` finds shallow modules, scattered knowledge, leaks and parts that cannot be tested through their interface, with before/after pictures; `unused` runs knip read-only (it stops when the packages are not installed), checks each finding once more with a search, and splits them into "safe to remove" and "check first"; `security` runs gitleaks (whole git history, secrets never shown in full), semgrep and the package audit, installing the first two on the machine on first run, adds the model's reading of rights checks, input, queries, uploads and webhooks, marks each tool finding real or likely false alarm, and sorts by severity; `performance` reads for code that looks slow and gives a first summary at once, and only when a suspicion needs numbers adds a measurement plan, which it runs on this machine after your yes, cleaning up after itself; `docs` uses `better-docs`' inventory (purpose, last change, stale, repeats, finished plans) and checks every path, command, setting, number and name in the documents against the code, without changing a document; `comments` finds comments that lie about the code, stale TODOs (with their age from `git blame`), code left commented out, and comments that only repeat the code; `todo` is the TODO part of `comments` on its own; `tests` finds important parts with no tests, tests that check nothing, switched off or passing by chance, runs only the doubtful ones (never a snapshot update) and measures coverage into the temp dir when the project can. `ai` checks code that calls an AI model against 63 numbered practices (failures and retries, watching and logs, tests, answer-quality checks, cost, several agents, security, the mobile client): every practice gets a mark in one table on the page — done, partly, missing, does not apply, or not checked with a question to you — and a key it finds is never shown in full; `llm` works too. A scan observes and never changes: running read-only tools, the doubtful tests or timings is allowed, writing code or data is not. `/scan` alone looks at the project and suggests which scan fits; it never starts one on its own. `/scan pin <command>` makes a separate `/scan-<command>` shortcut, `/scan unpin <command>` removes it. The item you pick comes back as a ready `/explore` or `/how` command. Built like Impeccable's `/impeccable`; `architecture` is adapted from Matt Pocock's `improve-codebase-architecture` (MIT).
- **[ask](./ask/SKILL.md)** — `/ask <command> [target]` answers questions about the code and changes nothing. `what-is-it` is the first look at a whole project, on a page with pictures and copy buttons (made with `scan`'s page style); `how <part>` explains one part in the chat the way a senior engineer onboards a colleague, and `how to <task>` adds where and how the new thing should go; `why` finds what led to the code's shape in history, PRs, tickets and docs, each claim marked found, converging, guessed or unknown; `zoom-out` maps the parts around a place. `/ask` alone suggests which fits. `/ask pin <command>` makes a short `/<command>`.
- **[how](./how/SKILL.md)**, **[how-to](./how-to/SKILL.md)**, **[why](./why/SKILL.md)**, **[zoom-out](./zoom-out/SKILL.md)** — shortcuts for `/ask how`, `/ask how to`, `/ask why` and `/ask zoom-out`; install them with `ask`.
- **[fix](./fix/SKILL.md)** — `/fix <command> [folder] [deep]` fixes what `/scan` found: by default on the current branch, with `deep` in the whole project. It reuses a fresh scan result (same project, same commit, same uncommitted changes) or runs the scan first, shows a numbered plan in the chat, and changes nothing before your "yes" (or "yes except 3, 7"). `docs` (what `better-docs` did, plus correcting false claims), `comments`, `todo`, `unused` and `tests` (test files only; it stops on a test that shows a bug) change the files, run the project's checks, roll back a change that breaks one, and leave everything uncommitted. `security`, `performance` and `architecture` change no code: they hand the chosen findings to superpowers' `brainstorming`, or plan here when it is not installed. `ai` splits the findings in two: small, local ones (model names in one place, a tool error returned to the model, `max_tokens`, the cache breakpoint, Claude Code's deny list) it fixes after your yes; the rest go to `brainstorming` with the matching ready example code. `scan ai` and `fix ai` are ported from the `agentic-sentinel` skill. A prompt copied from a scan page works as input too. `/fix pin <command>` makes a `/fix-<command>` shortcut.
- **[grill-me](./grill-me/SKILL.md)** — `/grill-me [plan]` stress-tests a plan, design or decision until the two of you understand it the same way. It keeps a tree of decisions and asks, round by round, every question whose prerequisites are settled (at most five), numbered, each with why it matters and a recommended answer, so "all as recommended except Q2" is a full reply. Facts it looks up itself, with `Explore` subagents that do not block the other questions. Changes nothing; ends with what was agreed, what is open, the words and decisions worth recording, and the next step after a yes. Adapted from Matt Pocock's `grilling` (MIT).
- **[grill-with-docs](./grill-with-docs/SKILL.md)** — `/grill-with-docs [plan]` is `grill-me` that reads the glossary and decisions first, turns clashes with them into questions, and records settled words and (after a yes) decisions along the way through `domain-model`. Install it with `grill-me` and `domain-model`.
- **[mockup](./mockup/SKILL.md)** — `/mockup [question]` answers a design question by letting people try it. Logic and states: one self-contained HTML file with free buttons and guided scenarios over a pure, liftable module, written to the OS temp folder and opened, ready to send to someone who does not code. Looks: 3–5 structurally different variants of a screen inside the running app, switched by `?variant=` and a bottom bar hidden in production builds, removed after the choice. Nothing is committed or branched; the answer can become a decision record through `domain-model`, and the proven code goes into the real code only after a yes, rewritten. Adapted from Matt Pocock's `prototype` (MIT).
- **[to-plan](./to-plan/SKILL.md)** — `/to-plan [spec]` is a short name for superpowers' `writing-plans`: it turns a spec into a step-by-step plan in `docs/superpowers/plans/`. Without an argument it takes the newest spec that has no plan yet. Needs superpowers installed; `brainstorming` already goes there on its own, so this is for when the spec exists and the plan does not.
- **[to-questionnaire](./to-questionnaire/SKILL.md)** — `/to-questionnaire [decision]` asks you only who it goes to and what you need back, then writes a questionnaire for that person to the OS temp folder: why, from/to, a context paragraph, how to answer, one-idea questions most important first with an empty answer line each, and "anything we did not ask?". Facts it can look up go into the context instead of the questions. Adapted from Matt Pocock's `to-questionnaire` (MIT).
- **[focus](./focus/SKILL.md)** — Shape output to be action-first and skimmable (ADHD-friendly). Toggle on with `/focus`, off with "stop focus mode".
- **[output-style](./output-style/SKILL.md)** — `/output-style ELI5` switches in one command, no picker; bare `/output-style` lists every style reachable from here (built-in, user, project, plugin) and asks. Brings back the standalone command Claude Code removed in v2.1.91.
- **[baby](./baby/SKILL.md)** — Say the last answer again in plain, non-technical words, then keep every reply that way. Works in the session you are already in, unlike the `Baby` output style.
- **[output-style-add](./output-style-add/SKILL.md)** — Turn a description into a real output style: brainstorm the role, tone and format, write `~/.claude/output-styles/<name>.md`, offer to switch to it.
- **[handoff](./handoff/SKILL.md)** — `/handoff <what the next session is for>` compacts the conversation into a handoff document for a fresh agent. It goes to the OS temp directory, not the workspace. It points at plans, commits and issues instead of copying them, redacts secrets and personal data, names the skills to call next, and marks what was not verified. The reply ends with the file path and one line to paste into the next session. `handoff-lpm` calls it, and the agent may reach for it on its own.
- **[handoff-lpm](./handoff-lpm/SKILL.md)** — `/handoff-lpm <what the next session is for>` does the whole move: it calls the `handoff` skill for the document, then opens a new tab in the lpm app with `lpm run --command claude --prompt ...`, which starts a fresh Claude session and sends it the one-line message that points at the document. Needs the lpm app running.
- **[to-spec](./to-spec/SKILL.md)** — `/to-spec [topic]` writes the feature you already talked through (in `explore`, `grill-me` or plain chat) as a spec in `docs/superpowers/specs/`, without interviewing you: problem, solution, user stories for every named behaviour, decisions (no paths, no code), testing, out of scope, and "Open questions" for whatever the talk did not settle, each with a recommendation, instead of guesses. Uses the glossary's words and respects written decisions. Not committed. Next: `/to-plan`, or `/grill-me` first when open questions change the design. Adapted from Matt Pocock's `to-spec` (MIT).
- **[update-plans](./update-plans/SKILL.md)** — `/update-plans <what changed>` for when you change your mind mid-work. It finds the superpowers spec and plan (`docs/superpowers/specs/`, `docs/superpowers/plans/`, or asks), finds every place the change makes wrong in both directions, and shows all edits at once — was → now, why — for one yes. Done `- [x]` steps keep their mark and get a new `- [ ] Rework: …` step after them. Only those two documents change: no code, no commit. With no argument it asks what changed; if the whole idea changed it recommends a fresh `brainstorming` instead of a patch. Borrowed from OpenSpec's update-change.
- **[verify](./verify/SKILL.md)** — `/verify [ticket | file]` checks that the code does what was promised. It finds the promise (the argument, the ticket key in the branch name, the branch's spec or plan files, or a list from the chat), splits it into items and asks you to confirm them. Then a fresh subagent proves each item: it runs the existing tests and the program, and writes any missing test in a temporary copy of the project (a detached git worktree with the uncommitted changes and linked dependencies), deleted afterwards. The project itself is never changed. The report is a table (proven / broken / not verified) with must / should / could fix findings and the text of each new test, ready to paste, with a failing one as where the fix starts. Report only: it never fixes and never says "ready" while something is not verified. Borrowed from OpenSpec's verify, which only reads the code; this one runs it.
- **[wtf](./wtf/SKILL.md)** — "That last message did not land: re-pitch it." The agent says it once more — goal, where we are, the point, what it needs from you — in ASD-STE100 Simplified Technical English and in your own names for things, then stops. One shot, and it keeps the technical words; `/baby` is the one that drops them and stays on.

## Model-invoked

- **[domain-model](./domain-model/SKILL.md)** — Keeps the project's language and big decisions written down while you work, without being called. A settled word goes straight into `docs/glossary.md` (one word per idea, the others listed as words not to use, only this project's words), with one line at the end of the reply. A decision is recorded in `docs/decisions/NNNN-slug.md` only when it is hard to undo, odd without its reason and a real choice, and only after one yes/no question; a proposal turned down for a lasting reason counts too, so `scan architecture` stops suggesting it. Projects with parts get `docs/glossary-map.md` and a glossary and `decisions/` per part, split after one question when one glossary stops working. While `ask`, `scan`, `explore` or `verify` run it writes nothing and offers its words at their end. `ask` and `scan` read these files first. Adapted from Matt Pocock's `domain-modeling` (MIT), with the files under `docs/`.
- **[rethink](./rethink/SKILL.md)** — Step back and rethink systematically after 3+ failed attempts at any task.
